# 平台规则（min-atoms，对所有项目生效，优先于项目内说明）

## 范围
- 只实现用户在需求清单里明确提出的功能。用户没提到的功能不要预先加，例如历史记录、登录注册、设置页、导出、统计图表；等用户提出再做。
- 先尽快写出能运行、页面上能看到的最小版本，再逐步完善，直到需求清单全部完成。

## 保护已有数据（重要）
- 应用数据库里已有的记录（包括以往执行留下的测试记录）属于用户。自测时不得删除、清空或修改已有记录，也不要点击会删除或修改已有数据的按钮；不得临时修改再还原。
- 自测优先只读：调用 GET 接口、查看页面、查询行数。搜索、筛选、排序等功能用读取验证，不为此做无关的写入测试。
- 确实需要测试写入时，只新建能识别的测试记录（有文本字段时以"[自测]"开头），保存本次执行创建时实际返回的 id（API 创建响应、INSERT RETURNING 或等价实际结果），后续写入只用这些 id，测完只按这些 id 删除这些记录。不得假设 id 从 1 开始或连续、把行位置或数组下标当作 id、猜测 id 或复用以往执行的 id。
- 修改或删除自测记录前（包括清理），先用保存的 id 读回记录，确认它属于本次执行新建的测试记录集合，有文本字段时还须核对"[自测]"标记；标记本身不能证明是本次执行创建的。无法确认就不修改或删除，跳过该写入测试。
- 禁止：调用"清空 / 全部删除 / 重置"类的按钮或接口；不带 id 条件的 DELETE 或 UPDATE；DROP 或 TRUNCATE；删除或替换数据库文件；用会清空数据的方式重跑迁移。
- 用户要求的删除、清空功能照常实现，但自测时不要对已有记录执行它；需要验证就用新建的测试记录。

## 构建完成后的回复
- 回复是写给最终用户看的：用简短的中文说明做了什么、怎么用，3–6 行即可。
- 不要在回复里贴 API 返回的 JSON、curl 命令或输出、文件路径、测试日志或代码片段。
- 用户主动询问技术细节时（例如在讨论中），可以正常解释。
